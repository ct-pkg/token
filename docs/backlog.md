- 状态词：`ready`（条件已具备、可实施）、`dormant`（只有规格、不产包）、`pending-decision`（待 owner 定）。

## 1 为什么这两件事挡在前面

包的对外身份由清单承载，目前只有 `name`、`version`、`licence`、`requires` 四键。要让包被安装到正确位置、
被构建器找到单元，还缺两个答案：这个包归谁发布、包内单元的根目录在哪。

包管理器侧已经能承载这两个答案：安装按发布方 / 包名 / 版本落盘，发布者字段必填；单元根必填并参与搜索根
展开；锁文件记录发布方与单元根；构建默认读锁并自动补搜索根；包索引也带这两项。因此缺字段不再是「写了没人认」，
而是「不写就装不上、也找不到单元」。

另一面，本仓还没有任何公开单元：清单再完整，装出来也是空包。

## 2 条目

### 2.1 清单补发布者与单元根

- **要做什么**：`ct.pkg` 增加发布者字段与单元根字段；将来若新增依赖，一律写成
  `<publisher>/<name>@<range>` 全名形式，不接受短名。
- **为什么需要**：安装落点与源解析靠发布者区分同名包；单元根决定构建时的搜索起点。
- **依据**：安装按发布方 / 包名 / 版本落盘且发布者必填；单元根必填并参与搜索根展开；锁文件记录发布方与
  单元根；构建默认读锁并自动补搜索根。两项字段已是安装与构建的硬要求，不是可选声明。
- **验收**：
  - 清单同时含两项，读取方解析无告警（现在即可验）；
  - 单元根指向的目录能作为构建搜索根解析到包内单元（需 2.2 先产出单元）；
  - 负例：删发布者 → 读取方非零退出并报缺键；单元根指到无单元目录 → 构建失败；依赖写短名 → 解析失败。
- **状态**：`ready`。字段可立即补；完整验收的最后一条等 2.2。

### 2.2 公开单元与规格占位

- **要做什么**：二选一——明确本包只是规格占位（没有公开单元，按 dormant 记录），或补上公开单元让包内检查
  通过。仅规格时不得为空包打 tag。
- **为什么需要**：包管理面要求「装了就能用」；只有规格没有单元的包若被当成可安装产物，就会产出空包。
- **等什么能力**：能检查包内是否存在公开单元的包管理器能力。当前没有，所以本条先按 dormant 登记。
- **验收**：
  - dormant 形态：本文件保留记录，仓库内无本包 tag；恢复条件写在本条；
  - 单元形态：包根出现公开单元，包检查退出 0 且至少识别到一个；
  - 负例：无单元时打 tag → 违约，按缺陷登记（撤回 tag 属对外操作，只由 owner 决定）。
- **状态**：`dormant`（本仓目前只有需求文档，没有公开单元）。
